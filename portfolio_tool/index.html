The product decision

So I wrote the PRD for what this data argues for.

If half of money-loss complaints are charges nobody agreed to, the fix is not better error handling. It is consent and visibility around automatic payments — and every wallet in the market has the problem, so whoever fixes it first can make a claim out of it.

  1. Warn before charging. 24 hours ahead, with "skip this one" and "turn it off".
  2. One Autopay screen. Every party that can charge, which linked bank it uses, last and next charge. Cancel in one tap.
  3. Confirm the first charge from a new party, or above a threshold the user sets.
  4. Nothing pre-ticked. Bundled add-ons default to off.

What would stop it: steps 3 and 4 add friction to paying, so payment success and legitimate recurring revenue are guardrails, with the threshold agreed before the test. And step 0 is checking this against internal tickets — if it is under ~10% of money-related tickets, it gets deprioritised.

Per-wallet breakdown

Shares are weighted and computed within each wallet’s own complaints, so a bigger review base doesn’t inflate them. ZaloPay’s review volume jumped from about 120 to about 3,000 a week in October, with 5-star share going 35% → 96%, which is why nothing here uses “total reviews” as a denominator.

Developer replies

“Boilerplate” = a reply whose first 70 characters match at least five others from the same wallet. ShopeePay answers 98% of complaints with two templates, so this measures automation coverage, not care.

How severity is graded

One question, asked in order. Stop at the first yes.

  1. S1 — money lost, held, at risk, or taken without the user agreeing.
  2. S2 — can’t do a core job: sign up, log in, transfer, pay, top up, withdraw.
  3. S3 — annoying but still usable: a published fee, a promotion that didn’t apply, lag.
  4. S4 — everything else: suggestions, vague criticism, praise.

Star ratings, swearing and the word “scam” never raise the level. A published fee someone finds expensive is S3; money taken without agreement is S1. Support complaints inherit the severity of the problem underneath.

Every predicted S1, and every case where the agent and the keyword baseline disagree about S1, routes to a person — 11% of reviews. An agent that quietly decides what counts as “someone lost money” isn’t a system I’d hand to a team.

How it was evaluated

157 reviews were used while tuning prompts and never counted. A separate 80-review test set was labelled by hand before the model ran on it once, scored once, never revised. The failure condition was set up front: if the keyword baseline reached 90% of the agent’s quality, the honest conclusion was that this doesn’t need a language model.

Limits, and where I got it wrong

My first labelling pass marked 36% of reviews S1 and produced no S3 at all: I was grading anger, not consequence — the exact mistake this tool exists to fix. My two passes agreed on only 15 of 53 complaints. Later, reviewing 31 disagreements between me and the model, I changed 26 labels and 25 went the model’s way. That is automation bias, which is why the headline numbers come from a test set I labelled blind.

Android only; people who hit a problem write reviews more often, so this compares wallets against each other rather than measuring satisfaction. Seven S1 cases in the test set is small — 7 of 7 gives a 65–100% interval. I found no clear case of users tricked into paying; in reviews “scam” is almost always anger or shorthand for an unauthorised charge, so that needs support tickets instead.
